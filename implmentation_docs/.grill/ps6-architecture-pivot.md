# Grill: PS6 architecture pivot — Jetson removed, backend-centric compute
Date: 2026-09-28

## Intent
Originally: create Document 06 (Implementation Plan). Mid-grill, the user revealed the actual hardware plan diverges fundamentally from master_approach.md's frozen architecture, requiring the architecture itself to be amended before any further document (including 06) can be written coherently.

## Constraints
- The user made this change deliberately and explicitly, including consciously dropping master_approach.md's most-repeated safety invariant ("local siren must not depend on Internet access") after I surfaced that consequence directly. This is not a misunderstanding to correct — it is the user's informed choice for their build.
- The user chose (of three options offered) to revise documents 01-05 first, then produce Document 06 against the corrected set, rather than writing 06 as a standalone superseding document or treating this as BOM-only.

## Key decisions
- Decision: No Jetson Orin Nano Super, no local edge-AI compute device at all. Reason: user's explicit, repeated statement across four separate clarifying exchanges ("I won't use jetson nano for the prototype"). Alternative considered: swapping to a cheaper/smaller edge-AI device while keeping the edge-first pattern -- explicitly offered as an option and rejected by the user in favor of removing edge compute entirely.
- Decision: All computation (PPE/fire/smoke vision inference AND the full contextual decision engine) moves to the cloud backend. Reason: user's explicit statement ("The computation part will be done by the backend of our app... The app will do the rest"). This directly reverses master_approach.md Section 3.1 ("Edge-first AI: video should be processed locally instead of continuously uploading raw CCTV footage").
- Decision: Cameras must be cloud-push-capable (continuous streaming directly to the backend), not the BOM's originally recommended "RTSP-capable IP cameras rather than closed cloud-only cameras." Reason: user confirmed no local relay device exists to pull RTSP and forward it, and confirmed continuous streaming (not periodic snapshot upload) as the mechanism. This is a direct reversal of PS6_Complete_BOM.md's explicit camera recommendation.
- Decision: ESP32 is a pure Modbus-to-cloud gateway and remote-commanded actuator, with zero local decision authority. Reason: user's explicit, repeated confirmation across three exchanges: (1) ESP32 only fetches Modbus readings and sends them to the DB via GSM; (2) ESP32 has no role in deciding to fire the siren -- that requires the app; (3) ESP32 does execute the physical relay/siren switch, but only on a remote command received over GSM from the backend, never on its own local sensor threshold. This eliminates the entire "ESP32 defense-in-depth watchdog fallback" design from 02_TRD.md §12.2.
- Decision: master_approach.md's core safety invariant -- "a critical local safety action must not depend on Internet access" (§3.3) -- is deliberately dropped. Reason: I surfaced this consequence explicitly before the user confirmed ("no it requires the app for siren, esp has no role in this"), so this is an informed trade-off the user is accepting, not an oversight. A GSM/backend outage now means no siren response at all.
- Decision: GSM (cellular) replaces the Jetson-hosted 4G LTE modem as the ESP32's connectivity to the backend. Reason: user's explicit statement. Author's assumption (not separately re-confirmed, flagged in the amended master_approach.md for correction if wrong): ESP32's built-in WiFi is preserved as a LAN-primary path with GSM as backup, adapting the original LAN->4G failover *concept* to the new hardware, rather than GSM being the only connectivity path -- this is the lowest-risk reading that doesn't contradict anything the user said and avoids re-litigating a failover concept that was never explicitly revoked.
- Decision: Zone sensor nodes may be Arduino Nano or STM8-based boards (both RS-485 Modbus RTU slaves, same register map), per the user's "stm8 or arduino nano as the subnet type." Not deeply investigated further -- treated as an MCU choice, not a protocol change.
- Decision: master_approach.md is amended in place (a clearly marked, dated amendment section) rather than silently rewritten, so it remains a single source of truth for future sessions without erasing the original frozen baseline's history. PS6_Complete_BOM.md gets a pointer note to the same amendment rather than a full rewrite, since the user's "revise 01-05" instruction was scoped to the five numbered implementation documents.

## Surfaced assumptions
- The user did not address LAN vs. GSM-only for the ESP32 explicitly; the WiFi-primary/GSM-backup assumption above is the author's best-effort continuity choice, flagged for correction.
- Camera-side network connectivity (how the cloud-push cameras themselves reach the internet -- facility WiFi/LAN vs. their own cellular) was not addressed and is left as an implementation detail/TBD in the revised documents, not a blocking question, since it doesn't change any decision already made.

## Out of scope
- No further architecture questions raised in this session beyond what was needed to make the pivot coherent enough to document -- revisiting deeper trade-offs (e.g. bandwidth cost of continuous cloud video streaming, cloud GPU inference cost) is left to the user's own judgment, not re-litigated here.
- The procurement-gating question originally being asked when the pivot began was never re-asked after the architecture stabilized; it was folded directly into 06_IMPLEMENTATION_PLAN.md as a "Prerequisite -- Hardware Procurement" section instead, scoped only to Track A (hardware/firmware), since the other tracks need no physical hardware to start.

## Resolution
Documents 01_PRD.md, 02_TRD.md (full rewrite), 03_APP_FLOW.md, 04_UI_UX_DESIGN_BRIEF.md, and 05_BACKEND_SCHEMA.md were all revised in place to match the amended master_approach.md. PS6_Complete_BOM.md received a pointer/summary amendment note rather than a full rewrite. 06_IMPLEMENTATION_PLAN.md was then written fresh against the corrected document set, organized into five parallel tracks (Hardware/Firmware, Camera, AI/Vision, Backend/Data, Dashboard) converging on a single sync point (Phase 10, the Contextual Decision Engine), per the parallel-tracks structure decision made earlier in this same session before the pivot was revealed.
